# /checkmcp — check and install the 1C MCP servers (bsl-analyzer stack)

This command checks that all MCP servers from the project catalog (`content/mcp-servers.json`; after 1c-rules installation, rendered into the active tool config such as `.cursor/mcp.json` / `.mcp.json` / `.kilo/kilo.json` / `opencode.json` / `.codex/config.toml`) are actually available in the current session, and helps start or install missing ones. For Kilo Code the rendered file uses the top-level `mcp` key with per-server `{ "type": "remote"|"local", … , "enabled": true }` — **not** the legacy `.kilocode/mcp.json` with `mcpServers` (current Kilo CLI / Kilo Code v7.x+ does not read that file).

The stack has **two transports** and they are checked differently:

- **stdio** — `bsl-analyzer-workspace` and `bsl-analyzer-reference` are launched by the client as a local process (`command: "bsl-analyzer"`, `args: [...]`). There is **no HTTP endpoint to ping**. They are "available" when the `bsl-analyzer` binary resolves on `PATH` (or the absolute path in the rendered config) and the server's tools appear in the current session. The index builds **lazily** — the tools can be present while the index is still warming up; that is normal, poll `search status` / `graph status` (and `diagnostics catalog` to confirm diagnostics responds — there is no `diagnostics status` action).
- **http** — `v8std` (public, `https://ai.v8std.ru/mcp`) and `1c-code-check-mcp` / 1С:Напарник (local wrapper, `http://localhost:8007/mcp`) are HTTP servers and **can** be probed.

The canonical, machine-specific setup is generated by the bsl-analyzer launcher itself — `bsl-analyzer mcp install` (see `/installmcp`). The repo's `content/mcp-servers.json` is a PATH-based, secret-free template (uses `bsl-analyzer` on `PATH`, run from the project root so `--source-dir .` resolves; no `EMBEDDING_*`, no `NAPARNIK_TOKEN`).

## Target server catalog

| id | Transport | Endpoint / launch | Purpose | External requirement |
|---|---|---|---|---|
| `bsl-analyzer-workspace` | stdio | `bsl-analyzer mcp serve --profile workspace --source-dir .` | Project index: code search (`search`), call graph (`graph`), metadata (`metadata`), analyzer diagnostics (`diagnostics`), SDBL query (`query`), live-IB BSL exec (`execute`) / debug (`debug`) | `bsl-analyzer` on PATH; semantic `search_code` needs `EMBEDDING_*`; live-IB `execute`/`query execute`/`debug` need the bsl-analyzer 1C extension published on the base |
| `bsl-analyzer-reference` | stdio | `bsl-analyzer mcp serve --profile reference` | Platform API reference & docs (`search`), exact API syntax (`syntax_help`), ITS expert help (`its_help`) | `bsl-analyzer` on PATH |
| `v8std` | http | `https://ai.v8std.ru/mcp` | v8std.ru development standards, ACC/BSLLS/EDT diagnostics (`v8std_search`, `v8std_get_page`, `v8std_get_related`, `v8std_explain_snippet`, `v8std_explain_diagnostics`) | Internet access (public service) |
| `1c-code-check-mcp` | http | `http://localhost:8007/mcp` | 1С:Напарник — AI review (`check_1c_code`, `review_1c_code`), AI drafts (`rewrite_1c_code`, `modify_1c_code`, `ask_1c_ai`), versioned docs (`search_1c_documentation`, `onec_help`, `config_help`, `diff_1c_documentation_versions`), ITS (`its_help`, `fetch_its`) | Local 1С:Напарник wrapper running and reading `NAPARNIK_TOKEN` from **its own** environment |

> The source of truth for the bsl-analyzer launcher, profiles and embedding setup is the bsl-analyzer documentation. The full comol→bsl-analyzer tool mapping is in `MIGRATION-bsl-analyzer.md` at the repo root.

## Algorithm

### Step 1. Determine the server set

1. If the project has `.ai-rules.json`, take the catalog from the active tool config referenced by the manifest (`.cursor/mcp.json` / `.mcp.json` / `.kilo/kilo.json` under the `mcp` key / `opencode.json` under the `mcp` key / `.codex/config.toml` under `[mcp_servers."<id>"]`). A leftover `.kilocode/mcp.json` is **legacy** — ignore it; current Kilo CLI / Kilo Code (v7.x+) does not read it. In `opencode.json` the server keys are letter-normalized: a leading `1c`/`1C` becomes `onec` (`1c-code-check-mcp` → `onec-code-check-mcp`), while `bsl-analyzer-workspace`, `bsl-analyzer-reference` and `v8std` already start with a letter and stay unchanged — match servers to the canonical ids by the bare tool names below, not by the prefix.
2. Otherwise use `content/mcp-servers.json` from the rules repository.
3. If neither source exists, use the table above as the default set.

### Step 2. Check availability in the current agent session

For each `id`, determine **TOOLS_OK** / **TOOLS_MISSING** from the current session tool schema:

- **TOOLS_OK** — this server's tools are visible. Expected tools per server:
  - `bsl-analyzer-workspace` — `search`, `graph`, `metadata`, `diagnostics`, `query`, `execute`, `debug` (action-dispatched: one tool name + an `action` parameter).
  - `bsl-analyzer-reference` — `search`, `syntax_help`, `its_help`.
  - `v8std` — `v8std_search`, `v8std_get_page`, `v8std_get_related`, `v8std_explain_snippet`, `v8std_explain_diagnostics`.
  - `1c-code-check-mcp` — `check_1c_code`, `review_1c_code`, `rewrite_1c_code`, `modify_1c_code`, `ask_1c_ai`, `search_1c_documentation`, `onec_help`, `config_help`, `diff_1c_documentation_versions`, `its_help`, `fetch_its`.
- **TOOLS_MISSING** — no tools are visible in the schema.

If status is **TOOLS_OK**, treat the server as working. For the stdio workspace server, additionally confirm the index state (Step 3a). Do not treat "still building" as a failure.

### Step 3a. stdio servers — `bsl-analyzer-workspace` / `bsl-analyzer-reference`

There is **no HTTP endpoint** for these — do not try to ping a port.

- **TOOLS_OK** — call a cheap discovery action to confirm the server responds and inspect index progress: `search status`, `graph status`, and `diagnostics catalog` (diagnostics has no `status` action) on the workspace server. If a status reports the index is **still building**, that is **normal** (the index builds lazily on first use / file change). Re-poll `search status` / `graph status` until it reports ready; semantic `search_code` is only available once `EMBEDDING_*` is configured and the embedding index is built, otherwise `find_code` (lexical) / `graph` / `metadata` work immediately.
- **TOOLS_MISSING** — the client did not launch the process. Diagnose the launch, not a port:
  1. **Is `bsl-analyzer` resolvable?** PowerShell: `Get-Command bsl-analyzer -ErrorAction SilentlyContinue` (or check the absolute binary path the rendered config uses). If it is not on `PATH`, the stdio server cannot start.

     ```powershell
     $bin = (Get-Command bsl-analyzer -ErrorAction SilentlyContinue).Source
     if (-not $bin) {
         Write-Host 'bsl-analyzer NOT on PATH — stdio MCP servers cannot launch. Install bsl-analyzer and/or run `bsl-analyzer mcp install` to write an absolute-path entry.'
     } else {
         Write-Host "bsl-analyzer found: $bin"
         & $bin --version
     }
     ```
  2. **Is the rendered config entry correct?** For stdio it must carry `command` + `args` (or, per client, `{ "type": "local", "command": [...] }`), launched from the **project root** so `--source-dir .` resolves. The PATH-based template assumes the binary is on `PATH`; if it is not, regenerate the entry with an absolute path via `bsl-analyzer mcp install --target <tool> --preset recommended --source-dir .` (see `/installmcp`).
  3. **Did the client load it?** Restart the AI client (Cursor / Claude Code / Codex / OpenCode / Kilo Code) so it re-launches the stdio process and re-reads the config.

### Step 3b. http servers — `v8std` / `1c-code-check-mcp`

For servers with **TOOLS_MISSING** that are HTTP-based, probe the endpoint. PowerShell:

```powershell
$httpServers = @(
    @{ Id = 'v8std';            Url = 'https://ai.v8std.ru/mcp' },
    @{ Id = '1c-code-check-mcp'; Url = 'http://localhost:8007/mcp' }
)
foreach ($s in $httpServers) {
    try {
        $r = Invoke-WebRequest -Uri $s.Url -Method Get -TimeoutSec 5 -UseBasicParsing -ErrorAction Stop
        Write-Host ("{0,-20} {1}" -f $s.Id, ("HTTP " + [int]$r.StatusCode))
    } catch {
        $code = if ($_.Exception.Response) { [int]$_.Exception.Response.StatusCode } else { 'down' }
        Write-Host ("{0,-20} {1}" -f $s.Id, $code)
    }
}
```

Any HTTP response (even `405`/`400`/`406`) means the endpoint is listening — status **HTTP_OK**. Full timeout / `Connection refused` means **HTTP_DOWN**.

- `v8std` **HTTP_DOWN** — usually no internet access (it is a public service); check connectivity / proxy. There is nothing to install locally.
- `1c-code-check-mcp` **HTTP_DOWN** — the local 1С:Напарник wrapper is not running. Start it; it must read a `NAPARNIK_TOKEN` from **its own** environment (the token is **not** stored in `mcp-servers.json`). Without the wrapper its tools simply do not appear and the rules fall back to `diagnostics` + v8std for review.
- `1c-code-check-mcp` **HTTP 401 / 403** — the wrapper is up but the token is missing / wrong; fix `NAPARNIK_TOKEN` in the wrapper's environment and restart it.

### Step 4. Install / configure missing servers

There are no Docker containers in this stack. Configuration is done by the bsl-analyzer launcher and (for 1С:Напарник) by running the wrapper.

- **stdio servers** — generate the canonical entry with the launcher (do not hand-edit unless necessary):

  ```bash
  bsl-analyzer mcp install --target <tool> --preset recommended --source-dir .
  # <tool>: claude | cursor | codex | opencode | kilo  (per the bsl-analyzer docs)
  # optionally add EMBEDDING_URL / EMBEDDING_MODEL / EMBEDDING_DIM / EMBEDDING_API_KEY
  # to enable semantic search_code (lexical find_code works without it)
  ```

  See `/installmcp` for the full flow and `/updatemcp` for `--launcher-update`. The repo template is the PATH-based fallback.
- **`v8std`** — no install (public HTTP). Just ensure internet access.
- **`1c-code-check-mcp` (1С:Напарник)** — start the local 1С:Напарник MCP wrapper on its port (default 8007) with `NAPARNIK_TOKEN` set in the wrapper's environment. Do not put the token in the repo.

### Step 5. After install / start

1. For stdio servers, the index may need warm-up — poll `search status` / `graph status` until ready (`diagnostics catalog` confirms diagnostics responds). "Still building" right after launch is normal.
2. Re-run the http probe (Step 3b); HTTP statuses should become **HTTP_OK**.
3. If a server is absent from the active tool MCP config, add the entry — prefer regenerating via `bsl-analyzer mcp install` (stdio) or via the 1c-rules installer; manual fallback uses `adapters/<tool>.yaml → mcp.schema` and `content/mcp-servers.json`.
4. Restart the client (Cursor / Claude Code / Codex / OpenCode / Kilo Code) so it relaunches stdio processes and reinitializes the MCP session.
5. Run `/checkmcp` again; Step 2 statuses should become **TOOLS_OK**.

## Final report

Summary table for the user:

| Server | Transport | Session tools | Endpoint / launch | Action |
|---|---|---|---|---|
| `...` | stdio / http | OK / missing | OK / down / building | none / fix PATH / `bsl-analyzer mcp install` / start Напарник wrapper / reconnect client |

Under the table, list clear next steps with copy-ready commands. Do not list items that already work. Distinguish "still building" (wait / poll status) from "missing" (fix launch / config).

## Limits

- stdio servers have **no HTTP endpoint** — never report them as "down" because a port did not answer; check `bsl-analyzer` on PATH and tool presence in the session instead.
- The index builds lazily; a freshly launched workspace server reporting "still building" is **normal**, not a failure — poll `search status` / `graph status`.
- Semantic `search_code` is **disabled** until `EMBEDDING_*` is configured; lexical `find_code`, `graph`, `metadata`, `diagnostics` work out of the box.
- 1С:Напарник needs a running local wrapper and a `NAPARNIK_TOKEN` in the wrapper's own environment; the token is never stored in `mcp-servers.json`.
- The command does not start the Напарник wrapper or install bsl-analyzer without user confirmation.
